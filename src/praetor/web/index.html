What this console does

Praetor is a coordinator for autonomous agents. You (the operator) register your agents once (workers), then hand Praetor jobs. It picks the best worker using each one's past track record — held in Sibyl Memory — dispatches to it, verifies the result, and (when Base & Virtuals are connected) settles payment on-chain. Workers never open this UI; nor does the operator drive Praetor from it. All interactions are HTTP calls to the API — this page shows what those calls produced.

  1. Register your workersA one-time POST /api/workers per agent. See §03.1. Registered agents show up in §01 · Workers.
  2. Submit a jobPOST /api/jobs from your client, script, or upstream service. See §03.2. Praetor picks a worker, dispatches, verifies, and (if configured) settles USDC on Base.
  3. Inspect the evidenceReputation updates in §01, live counters + full-text history in §02 · Memory. Every routing decision leaves a receipt in Sibyl.

The actor model

  • You (operator) — the only human. You register workers, submit jobs, and monitor state via the API. This UI shows what those calls produced.
  • Worker (agent) — an autonomous process running on your infrastructure. It never opens this UI. Praetor holds a record of it (name, capabilities, wallet, ACP id) and calls it when a job matches.
  • Client (upstream) — whoever hands jobs to Praetor. Usually your product's backend, a script, or another agent. Talks to POST /api/jobs.
  • Praetor (coordinator) — this server. Picks the highest-reputation matching worker, dispatches, verifies, records, settles.

3.1 · Register a worker — one-time, per agent

Praetor stores an entity in Sibyl Memory keyed by name. Repeat calls with the same name update capabilities/wallet/ACP id in place — reputation is never overwritten.

POST /api/workers

Fields: name and capabilities are required. wallet receives USDC payouts on Base. acp_agent is the Virtuals ACP agent id/keyword used for delegation. max_value_usdc caps what this worker can be routed.

3.2 · Submit a job — route, run, verify, settle

Praetor picks the highest-reputation eligible worker, invokes the executor, runs the result through the verifier, and — if Base is configured with a signer — settles USDC. Only workers whose capabilities include the category are eligible; if none match, the call returns 400.

POST /api/jobs

The response includes routed_to, verified, routing_trace (the semantic-search-aware decision), acp_reference (Virtuals ACP job id), and payment_reference (Base tx hash or dryrun:…). On mainnet with value_usdc > 0, real USDC moves from the signer wallet.

3.3 · Retire a worker

The worker leaves the active routing set, but its events and receipts stay in Sibyl Memory — the audit trail is preserved.

DELETE /api/workers/<name>

How Praetor reaches the worker

When a job routes, the server invokes an executor function with the winning WorkerProfile and Job. The shipped default emits a deterministic signed report so verification and settlement paths run on real content. To dispatch to a real agent:

  • HTTP executor (simplest) — swap _executor in src/praetor/api.py to forward the task to your worker's endpoint and return its response as a JobResult. Your worker exposes whatever URL and auth it likes; Praetor is the caller, not the callee.
  • Virtuals ACP delegation — set VIRTUALS_* env vars (see .env.example) and register the worker with an acp_agent id. Praetor opens an ACP job against the agent's on-chain account.
